# Events and waiting

A `step({ waitFor })` pauses until another system reports back, such as a webhook, queue consumer, or approval action. Declare event payload schemas in the wizard's `events` option and deliver them with `run.send()`.

```ts file="packages/docs/snippets/learn/events.mts"
```

1. `events` declares `approved` with a payload schema.
2. `start()` enters `waitForApproval`. The run is `waiting`.
3. `send('approved', { by: 'Grace' })` checks the payload and calls the active handler.
4. The handler updates context and completes the wait. The step follows `next: 'done'`.

Returning nothing from a wait handler completes the step with the payload as output. Return `{ done: value }` to select another output, `{ keep: true }` to keep waiting, or `{ fail: 'reason' }` to fail the wait. Handlers do not return a routing target; put `next` on the step.

`waitFor` belongs to a standalone wait step. Place a runnable, view, or child step after it. Those declarations still support ordinary `on` handlers while active, without blocking on an event before their work.

`send()` reports delivery or buffering for this event. It does not wait for the run's outcome. Use `awaitOutcome()` to observe the next waiting, halted, or terminal state, or `awaitResult()` when you will keep driving the run to completion.

## Invalid payloads

Typed payloads catch known mistakes before execution. Bodies from a webhook or queue enter as `unknown` and still get a runtime check:

```ts
const body: unknown = {}
const sent = await run.send('approved', body)
if (!sent.ok && sent.reason === 'rejected') console.error(sent.issues)
```

An invalid body returns `BOUNDARY_REJECTED`. The handler never receives it and the wait stays active.

## Timeouts and delays

```ts
awaitDecision: step({
  waitFor: {
    'approval.decided': ({ payload, update }) => {
      update({ decision: payload })
      return { done: payload }
    },
  },
  timeout: { after: '48h', next: 'expired' },
  next: 'route',
}),
```

The deadline is absolute. If the process stops after three hours, resume leaves 45 hours on the original deadline. If it resumes after that deadline, the timeout fires before an event can complete the wait.

At timeout the wait completes with output `undefined` and activates `expired`. Its `OutputOf` type includes `undefined`, and that type reaches consumers through `needs`. Check the value before reading payload fields, even when the need is a plain step reference.

For a delay without an external event, use `step({ sleep: '10m', next: 'checkAgain' })`. The sleep deadline also survives restart. A convenience `wizard.run()` keeps waiting through pure sleep timers and retry backoff; it returns a snapshot when input from a person or external system is needed.

## Events that arrive early

A valid event sent to a started run with no active listener is buffered for five minutes by default. OpenWizard delivers it when a matching listener becomes active. Set the policy in the wizard options:

```ts
unmatchedEvents: { buffer: true, ttl: '30m' },
```

With `buffer: false`, an unmatched event returns a dropped result. Sending before `run.start()` returns `FLOW_NOT_STARTED`.

## Duplicate deliveries

Use the sender's stable delivery id when retries may deliver an event twice:

```ts
await run.send('approved', { by: 'Grace' }, { eventId: 'approval-delivery-42' })
```

OpenWizard stores recent event ids in the snapshot. A duplicate returns `{ ok: true, duplicate: true, delivered: [] }` without invoking handlers again. Set `eventIds: { ttl: '24h', limit: 1_000 }` in run options to choose the retention window and size; those are the defaults.

## Routing shared streams

Give each run a `correlationId` when one event stream serves many runs. A wizard's `correlate` option can extract that id from the payload:

```ts
const checkout = defineWizard(
  {
    name: 'checkout',
    context: z.object({ orderId: z.string() }),
    events: { 'payment.captured': z.object({ orderId: z.string(), paymentId: z.string() }) },
    correlate: { 'payment.captured': (payload) => payload.orderId },
  },
  ({ step, steps }) => steps({
    payment: step({ waitFor: { 'payment.captured': ({ payload }) => ({ done: payload.paymentId }) } }),
  }),
)

const run = checkout.create({ orderId: 'o-1' }, { correlationId: 'o-1' })
```

An event with another run's correlation id is dropped. Correlation chooses the run that receives data; your host must still authenticate the sender. See [external event routing](/advanced/events).
