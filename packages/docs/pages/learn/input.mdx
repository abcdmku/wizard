# Views and input

A `view` pauses the run at a form. It stores a draft and validates it when your application moves on. The accepted value is the view's output, and a later step reads it through `needs`.


1. `start()` enters `contact`. Status is `waiting` and `state.current` is `'contact'`.
2. `setInput('contact', patch)` shallow-merges the patch into the draft and clears issues for changed fields.
3. `next()` parses the whole draft with `input`. On success the parsed value becomes the step's output, and `done`, which needs it, starts.
4. `done` reads the accepted email from `needs.contact` and completes.

`setInput()` stores the draft. `next()` attempts to leave the view.

## Invalid input

```ts
const moved = await run.next()

if (!moved.ok && moved.reason === 'validation') {
  console.log(moved.code) // 'INVALID_INPUT'
  console.log(moved.issues) // [{ message, path }]
}
```

The run stays on the view, `exit` does not run, and no later step starts. Render the issues and let the user edit the draft. `run.validate('contact')` checks without trying to move. `canEnter` and `canExit` can also refuse navigation.

## Draft and context are separate

The draft belongs to the view while it is edited. Once `next()` accepts it, the parsed value is the view's output. A later step reads it with `needs: { contact }`, typed by the `input` schema.

Context holds facts known when the run is created. A view can still change one in `exit`, for example a field that a [projection](/advanced/projections) sends to the client:

```ts
exit: ({ output, update }) => update({ express: output.express }),
```

`back()` preserves the draft and does not run the view's `exit` hook.

## Initial drafts

`initial` seeds the draft from a partial object or a function of `context` and `deps`:

```ts
profile: view({
  input: profileInput,
  initial: ({ context }) => ({ plan: context.selectedPlan }),
  next: 'done',
}),
```

OpenWizard stores the resolved draft, so back navigation and resume keep it. `resetInput('profile')` clears it and runs the initializer again. An initializer that throws fails the view.

A view can handle declared events through `on`. To require approval before entering the form, place a separate `step({ waitFor })` before it.

## Where data is checked

| Boundary | Checked by |
|---|---|
| Starting context | `wizard.create(input)` |
| View draft | `next()`, `go()`, `validate()` |
| Event payload | `send()` |
| Work output | The step's optional `output` schema |

`boundary.trusted<T>()` supplies a type without checking values at runtime. Use it for data your host already checks, such as service dependencies.
