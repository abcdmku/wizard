# Save and resume

A live run belongs to one process. A snapshot records its state so another run object can continue after that process stops.

```ts file="packages/docs/snippets/learn/persistence.mts"
```

1. `first` starts and waits at the `contact` view with a saved draft.
2. `save()` writes the snapshot under `signup-1` and waits for storage.
3. `dispose()` frees the old object. The stored snapshot stays.
4. `signupWizard.resume(snapshot, options)` creates `second` using the same wizard definition.
5. `second.next()` continues with the draft.

Each resume increments `run.epoch`, which distinguishes new snapshot and mirror frames from those emitted before resume.

## What is saved

A snapshot includes the run id, definition name and version, context, step records, timers, buffered events, recent event ids, and child snapshots. Item work also retains its input list and finished results. The snapshot does not include the wizard definition or service dependencies.

Use the same wizard to resume and supply the services it still needs. Dependencies bound with `wizard.provide(deps)` are available when that wizard resumes a run too.

```ts
const saved = await store.get('signup-1')
const second = signupWizard.resume(saved, { store })
```

Resume uses the original absolute timer deadlines. Each run handles overdue timers before recovering its own interrupted work. Finished steps and finished items stay finished; external calls interrupted before their result was saved require idempotent recovery. See [retries and idempotency](/advanced/recovery).

## When snapshots are written

```ts
const run = signupWizard.create({}, { instanceId: 'signup-1', store })
```

With a `store`, each state change schedules a write. Call `save()` when your next action requires that write to finish. Set `autoSave: 'off'` in run options to write only on `save()`.

`createMemoryStore()` is for tests and examples. For a database, implement `Store` with `get`, `set`, and `delete` for one snapshot per key.

## Outcomes with snapshots

`wizard.run(input)` disposes its live run after reaching an outcome. A `waiting` or `halted` outcome carries the snapshot you need to continue:

```ts
const outcome = await signupWizard.run({})
if (outcome.status === 'waiting') {
  const resumed = signupWizard.resume(outcome.snapshot)
  await resumed.setInput('contact', { email: 'grace@example.com' })
  await resumed.next()
  resumed.dispose()
}
```

`run.awaitOutcome()` gives the same outcome kinds while keeping an existing run alive. It is useful when your process owns the run and will send more input itself.

## Keep it serializable

Snapshots must survive a JSON round trip. Store dates as ISO strings and keep functions, class instances, `Map`, and `Date` out of context and outputs. Invalid data fails the write with `SNAPSHOT_NOT_SERIALIZABLE` and its path before the store overwrites anything.

## One owner per run

Core expects one process to own each run. When several workers can touch the same key, use [`@openwizard/durable`](/packages/durable) for leases, fencing, and command deduplication. [Snapshots and migrations](/advanced/persistence) covers stored state when the definition changes.
