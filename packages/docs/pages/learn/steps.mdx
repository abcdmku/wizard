# Steps

A step is a named stage in a flow. Its kind tells OpenWizard whether to run code now, pause for something outside the process, choose another route, or finish.

Most small background workflows need only a `task` followed by a `final` step. This example downloads a report and then finishes:


`download` runs when the flow starts. If its function succeeds, OpenWizard stores the returned string in `run.getState().steps.download.output` and follows `next: 'done'`.

`done` creates the final output and changes the run status to `done`. That output is what `awaitResult()` returns.

## How a run moves between steps

The flow needs an entry point and links between later steps.

1. `start()` activates the configured start step.
2. An automatic step such as a task runs as soon as it becomes ready.
3. When the step finishes, its `next` value names the next step.
4. A waiting step stops that automatic progress until your application sends a command or event.

There is no hidden loop over the object. After the start, the `next` links and decision results control where the run goes.

## Choose a kind based on what finishes the step

| Kind | What it represents | What finishes it |
|---|---|---|
| `task` | Code your application can run, such as a database write or API call | The task function resolves |
| `view` | A screen or form that needs user input | Your application calls `next()` with a valid draft stored |
| `wait` | A pause for an external event, such as payment confirmation | Your application calls `send()` with an event handled by the step |
| `decision` | A routing choice based on current data | Its `next` function returns one or more step ids |
| `flow` | Another flow run owned by this parent step | The child run finishes |
| `final` | The successful end of the flow | Its output function returns |

You will rarely use all six in one flow. Pick the kind that matches who or what can complete that stage.

### Use `task` for code that can run now

A task starts automatically when it is ready. Its function may return a value or a promise. Use tasks for database calls, HTTP requests, file work, or calculations that you want OpenWizard to track.

If the function rejects or throws, the task fails. You can add a retry policy, timeout, output schema, or compensation function when the call needs them.

### Use `view` when a person controls progress

A view makes the run wait at a user-facing stage. Your UI stores a draft with `setInput()` and tries to leave with `next()`. OpenWizard checks the draft before it moves.

The [input page](/learn/input) walks through that lifecycle.

### Use `wait` when another system controls progress

A wait step listens for declared flow events. A payment provider, queue consumer, or webhook route can call `send()` when the outside action happens.

Unlike a task, a wait does not poll or call the outside system. It stays active until an event handler finishes it or an optional timeout sends the run elsewhere.

### Use `decision` to choose a route

A decision runs a function that returns a step id. It should inspect data and choose a route, not perform the business work for that route.

For example, a delivery decision can return `'express'` or `'standard'`. Only the chosen task becomes ready.

### Use `flow` to run a child workflow

A flow step creates a child run from another flow definition. The parent step stays active while the child runs. When the child finishes, its output becomes the parent step's output.

Use this when the child has several steps, its own tests, or is reused by more than one parent. A task is simpler for a single function call.

### Use `final` to return success

A final step ends the run successfully. Its optional `output` function reads context and dependencies and returns the flow's public result.

A final step has no `next` link because the successful path ends there.

## How OpenWizard chooses the first step

If you omit the `start` option, OpenWizard uses the first key in the steps object. In the report example, `download` comes first, so it starts first.

For anything beyond a tiny flow, naming the start step makes the entry point clear and prevents a later reordering of the object from changing behavior:

```ts
const flow = builder.steps(
  {
    first: builder.task(doWork, { next: 'done' }),
    done: builder.final(),
  },
  { start: 'first' },
)
```

`{ start: 'first' }` does not run the step by itself. It tells `run.start()` which step to activate.

An array such as `{ start: ['loadProfile', 'loadOrders'] }` activates several entry steps. Use that only when the work is independent and you understand how the branches join again. The [parallel work recipe](/recipes/parallel) shows the complete shape.
