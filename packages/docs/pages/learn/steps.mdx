# Step kinds

The `defineWizard` callback provides `step`, `view`, `flow`, and `steps`. Each constructor takes an object configuration. Return `steps(map, { start? })` to assemble the definition.

| Declaration | Purpose |
|---|---|
| `step({ run })` | Run synchronous or asynchronous work |
| `step({ each, run, concurrency? })` | Run work for each item and collect outputs in input order |
| `step({ waitFor })` | Wait for a declared external event |
| `step({ sleep })` | Wait until a persisted timer is due |
| `step({ next, targets? })` | Route or join without a work callback |
| `view({ input, ...config })` | Collect and validate a draft |
| `flow(childWizard, config)` | Run a child wizard |

## Run work

```ts file="packages/docs/snippets/learn/task.ts"
```

The returned value, or resolved promise value, becomes the step's inferred output. Throwing or rejecting fails the attempt. Runnable steps support retry, timeout, compensation, idempotency, mapped errors, and fallback.

For a list of items, add `each: ({ context }) => context.items`. Its `run` callback receives `item` and `index`; the step output is an array in input order. `concurrency` bounds the number of item calls running at once. OpenWizard snapshots the item list and stores finished item results, so resume does not repeat finished items. An exhausted item retry fails the step; `run.retry('step')` retries failed items and keeps finished results.

## Choose the next step

```ts file="packages/docs/snippets/recipes/branching.ts"
```

`next` accepts a step id or object, an array to activate parallel branches, `null`, or a function returning those values. A function may be asynchronous and must declare `targets`. OpenWizard checks its return against those targets at runtime; an invalid return fails the step. Return `null` or omit `next` to end that branch.

A routing declaration, `step({ next, targets })`, has output `undefined`. A runnable step keeps its work's output and supplies that value to its `next` callback.

Literal ids are checked against the assembled map. Object references must belong to that map under exactly one key. Assembly checks declarations without executing their callbacks.

## Join typed outputs

Declare producers before the consumer so `needs` can reference their step objects:

```ts
const profile = step({ run: ({ context, deps }) => deps.loadProfile(context.userId) })
const orders = step({ run: ({ context, deps }) => deps.loadOrders(context.userId) })
const dashboard = step({
  needs: { profile, orders },
  run: ({ needs }) => ({ profile: needs.profile, orders: needs.orders }),
})

return steps({ profile, orders, dashboard }, { start: ['profile', 'orders'] })
```

`needs` both gates and activates its consumer. Producers do not need `next: 'dashboard'`. Every hook on the consumer receives typed `needs` values.

| Need | Value supplied to hooks | If producers are skipped |
|---|---|---|
| `profile: profileStep` | The producer's output | The consumer skips with reason `needs-skipped` |
| `winner: { any: [first, second] }` | The first completed output, typed as the union of producer outputs | The consumer skips only if all listed producers skip |
| `extra: { optional: extraStep }` | The output or `undefined` | The consumer can continue once the producer settles |

`needs` takes step objects so it can infer their outputs. `dependsOn` takes ids or objects and only checks completion. `dependsOn: [first, second]` gates on both, while `{ any: [first, second] }` gates on either. A skipped step satisfies this control gate. Supply an activation through `start` or `next` when using `dependsOn` alone.

## Wait for events or time

An event wait is its own step:

```ts
approval: step({
  waitFor: {
    approved: ({ payload }) => payload.accepted ? { done: payload } : { keep: true },
  },
  timeout: { after: '48h', next: 'expired' },
  next: 'publish',
}),
```

A `waitFor` handler can return `{ done: value }`, `{ keep: true }`, or `{ fail: 'reason' }`. Returning nothing completes the wait with the event payload as output. Wait handlers do not return `next`; declare routing on the step.

A timeout completes the wait with output `undefined` and activates its timeout target. The wait's `OutputOf` type includes `undefined`; hooks consuming it through `needs` must check for that value, even with a plain need.

Compose an event wait followed by a runnable, view, or child step. Those steps keep ordinary `on` handlers for events received while active. See [events and waiting](/learn/events).

Use `step({ sleep: '10m', next: 'checkAgain' })` for a delay. The timer has an absolute deadline in the snapshot, so restart does not begin another ten-minute wait. `sleep` also accepts a function of hook arguments and produces no output.

## Finish naturally

A final runnable step finishes after its work and exit hook. A final view finishes after `run.next()` validates and exits it. A child step finishes when its child completes. The wizard completes once its activated branches and hooks finish.

Without an options-level `output` selector, the wizard returns the output of the last completed sink. A sink has no static `next` or `targets` and is not a producer for another step's `needs`. Fallback and wait-timeout routes are alternate outcomes, so those edges do not remove the original step from sink selection. Several sinks produce a union of output types; skipped sinks or graphs without a sink can add `undefined`.

For a single result, use a final join with typed `needs`, or select it from context with `output: ({ context }) => ({ total: context.total })` in the wizard options. That selector runs synchronously after activated work finishes. Prepare asynchronous results in a runnable step.

## Views, children, and entry steps

A view stores a draft independently of rendering. See [views and input](/learn/input). Pass the child wizard itself to `flow(childWizard, config)`; its completed output becomes the parent step's output. See [composition](/getting-started#compose-wizards-and-step-modules).

The first map key is the default entry. Choose another with `steps(map, { start: 'load' })`, or start several branches with an array. OpenWizard checks those ids against the map.
