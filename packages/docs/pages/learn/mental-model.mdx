# Wizards and runs

A wizard is a typed definition of steps and their links. A run is one execution with its own context, input drafts, and step records. Store its snapshot to continue after a process restart.

<Diagram name="runtimeModel" />

Commands, external events, and timers change the recorded state. OpenWizard uses that state to decide which work starts next. A pending promise belongs to the live process; its completed result belongs to the snapshot.

## Definition and instance

`defineWizard(options, ({ step, view, child, steps }) => steps(map))` builds the definition once. Inspectors and integrations accept the wizard itself, so use `inspect(order)`, `createDurableHost(order, options)`, or `child(order, config)`.

Create a run when you have input for one execution:

```ts
const run = order.create(
  { orderId: 'o-42', total: 42 },
  { deps: { payments }, instanceId: 'order-o-42' },
)

await run.start()
```

- `steps(map, { start })` assembles step references and chooses the entry steps. Invalid references and dependency cycles fail at definition time.
- `wizard.create(input, options?)` checks starting context and returns a `Run<typeof wizard>`.
- `deps` supplies services such as database clients. Snapshots never store them. `wizard.provide({ payments })` binds services to a new wizard for its runs and integrations.
- `run.start()` activates the entry steps. `next` and `needs` decide which steps activate after that.

## What a run records

`run.getState()` returns the current state. `run.getSnapshot()` wraps it in a versioned JSON envelope for storage.

| Fact | Used for |
|---|---|
| Context | Typed data shared by this run's steps |
| Step records | Status, attempt, input, output, and error per step |
| Timers | Sleep, retry, wait timeout, and event-buffer deadlines as absolute times |
| Buffered events | Valid events that arrived before a listener was active |
| Compensation stack | Completed work and the outputs its undo hooks need |
| Child runs | Snapshots of nested runs |

## How a step becomes ready

| Declaration | Effect |
|---|---|
| `next: otherStep` | Activates that step when this one finishes |
| `next: [first, second]` | Activates several branches |
| `needs: { profile: loadProfile }` | Activates when `loadProfile` finishes and gives hooks its typed output as `needs.profile` |
| `when: predicate` | Skips the activated step if the predicate returns false |

A function `next` must declare `targets`, the step ids or objects it may return. Targets the function does not select become `skipped`. A target starts only when the function selects it, so a need on a target holds it and never starts it. For a data join over exclusive branches, use an `any` or `optional` need. A plain need propagates a skipped producer to its consumer.

`run.explain('step')` explains why a step is blocked. `run.waitingFor()` lists views, event waits, and sleep deadlines, including waits in children. See [graphs and parallel work](/advanced/graphs) for larger graphs.

## Save and resume

```ts
const saved = await store.get('order-o-42')
const resumed = order.resume(saved, { deps: { payments }, store })
```

Resume checks the snapshot against the wizard and restores its children. Each run fires its overdue timers before recovering its own interrupted work. Completed work stays completed; interrupted external calls need an idempotency policy. The [save and resume](/learn/persistence) page covers storage.
