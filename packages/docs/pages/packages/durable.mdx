# Durable

`@openwizard/durable` coordinates several processes that can touch the same run with leases, fencing tokens, command deduplication, and timer claims. You need it when two servers can handle commands for one run or two workers can wake one timer.

```sh
npm install @openwizard/durable @openwizard/core
```

```ts file="packages/docs/snippets/packages/durable.mts"
```

1. `createDurableHost(helloFlow, { store, ownerId })` hosts runs of the wizard by key.
2. `host.create('hello-1', input)` creates the run, or opens its existing record.
3. `host.dispatch(key, command, { commandId })` routes a command through lease, persistence, and deduplication gates.
4. `host.send(key, event, payload, { eventId })` delivers an external event through the same host.
5. `host.dispose()` waits for in-flight work, stops renewal, and releases its leases.

## Exports

| Export | What it does |
|---|---|
| `createDurableHost(wizard, options)` | Owns a keyed registry, leases, renewal, takeover, and disposal |
| `createDurableRun(wizard, options)` | Acquires a lease and creates or resumes one run |
| `resumeDurableRun(wizard, options)` | Acquires a lease and resumes only an existing record |
| `createMemoryDurableStore()` | In-memory `DurableStore` for tests and single-process demos |
| `createHostRegistry()` | Keyed host cache shared by a server's request handlers |
| `@openwizard/durable/store` | `DurableStore`, versions, lease, command, and timer protocols |
| `@openwizard/durable/testing` | Store adapter conformance suite |
| `DurableRunHost` | The run plus its lease, commit, dedupe, and timer gates |
| `DurableRunOpenResult` | `ok` or a code such as `LEASE_BUSY` with a `retryAt` |

## Boundaries

`LEASE_BUSY` means another worker owns the key; retry at `retryAt` and never run the command outside the host. The memory store cannot coordinate separate machines, so use [Drizzle](/packages/drizzle) or another database adapter in production. Execution is at-least-once: a worker can call an outside service and crash before saving the result. Pass the task's `idempotencyKey` to that service so it rejects or reuses duplicates.

## Command recovery

A repeated `commandId` replays its stored result and version. A different command using the same id returns `DEDUPLICATE_CONFLICT`. Completed results recover from their atomic state commit after a worker stops. If an applied command has no recoverable final result, the retry returns `COMMAND_INTERRUPTED`; inspect the run before choosing a new command id.

Pass `expectedVersion: { epoch, seq }` with a command id when the command depends on a state you already read. The host replays completed receipts first, rejects a new claim at the wrong version with `CAS_CONFLICT`, and checks again after asynchronous validation. A race during validation records `STALE`, so retries replay that refusal.

Event ids use the run's persisted deduplication window, which defaults to 24 hours and 1000 ids. These command and event checks coordinate stored state; external effects still need service-level idempotency.

Adapter authors import the protocol from `@openwizard/durable/store`. `CommitInput.applyDedupe` marks the claim `applied` atomically with the snapshot, preventing a new owner from applying it again. Run `durableStoreContract` from `@openwizard/durable/testing` against your store.
