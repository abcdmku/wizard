# Run steps in parallel

Start independent work together, then join its outputs with `needs`.

```ts file="packages/docs/snippets/recipes/parallel.ts"
```

## What happens

1. `steps(map, { start: ['loadProfile', 'loadOrders'] })` chooses both entry steps.
2. `run.start()` activates them and each produces its own output.
3. `join` declares `needs: { loadProfile, loadOrders }`. It activates once both outputs are ready, without either producer pointing `next` at it.
4. `join` reads typed values from `needs`, returns the combined result, and completes the wizard.

<Diagram name="parallel" />

A join can also need a step only to wait for it. Declare the need and ignore its value.

## Use the first completed result

```ts
const first = step({
  needs: { result: { any: [loadPrimary, loadReplica] } },
  run: ({ needs }) => needs.result,
})
```

The consumer activates when either producer completes. Its value has the union of their output types. It skips only if both producers skip. This does not cancel the other producer; the wizard still waits for activated work to finish.

A plain need skips its consumer when the producer skips. Use `{ optional: producer }` for data that may be absent; the consumer waits for that producer to settle and receives `undefined` when it skips. These rules matter when producers belong to exclusive branches.

## Map over items

When the number of tasks comes from input, use one item step rather than generating step ids:

```ts
fetchOrders: step({
  each: ({ context }) => context.orderIds,
  concurrency: 4,
  key: (orderId) => orderId,
  run: ({ item, deps }) => deps.loadOrder(item),
}),
```

The output array preserves input order even if requests finish out of order. OpenWizard stores finished items so resume does not repeat them, and manual retry keeps those results while retrying failed items. Item progress emits `{ done, total }` through `step.progress` events.

## Limit work across steps

Set `concurrency: 2` in the wizard options to bound concurrent runnable step work. Ready steps queue until a slot opens. Views and external event waits do not consume a work slot. An item step's own `concurrency` controls the calls inside that step.
