# Projections and the Mirror

A server run may contain secrets and internal state. A projection lists what may leave it. A
Mirror holds that projected state on a client and sends typed commands back.


This imports the assembled flow from [Steps and kinds](/concepts/steps). Both helpers accept the
live run instead of hiding how the host owns it.

`expose` is deny by default. Unlisted context keys and step fields are absent from both the runtime
value and its TypeScript type. Use `select` instead of `expose` for a custom derived shape.

`parseCommand` checks the command shape, step ids, event names, and JSON limits. `dispatch` parses
an input-event payload through its event boundary. A view draft reaches its input boundary when
the run validates or leaves that view. The host must still authorize the caller.

`createMirrorSource` adds sequence and run-instance checks for a transport such as SSE, WebSocket,
or `postMessage`.

On the client, `createMirror({ transport })` exposes projected state plus typed command helpers.
Nested commands follow child paths. The [Run REST API](/integrations/run-api) generates this
boundary for HTTP. [React](/concepts/react) binds it to hooks.
