# Core

The main entry exports authoring, runs, outcomes, persistence, and projections. Graph tools live in `@openwizard/core/inspect`, mirrors in `@openwizard/core/mirror`, and test helpers in `@openwizard/core/testing`. Full signatures are in the [generated reference](/typedoc/modules/_openwizard_core.html).

## `defineWizard(options, build)`

The build callback receives `{ step, view, child, steps }` and returns `steps(map, { start? })`. It runs once when you define the wizard. Context, event payloads, services, step ids, and outputs are inferred.

A wizard is the definition. Pass it directly to `inspect(wizard)`, `defineProjection(wizard, ...)`, `child(childWizard, ...)`, `createDurableHost(wizard, ...)`, and `createHTTP(wizard, ...)`.

| Wizard method | Contract |
|---|---|
| `create(input, options?)` | Validate input and return a live `Run` |
| `createAsync(input, options?)` | Create with asynchronous boundary validation |
| `resume(snapshot, options?)` | Restore a live run; accepts `migrate` |
| `resumeAsync(snapshot, options?)` | Restore with asynchronous validation or migration |
| `provide(deps)` | Return a new wizard with those service keys supplied |
| `run(input, options?)` | Start, await an outcome, and dispose the run |
| `runSync(input, options?)` | Return an outcome now, or throw `SYNC_VIOLATION` naming the step |

`provide` leaves the original wizard unchanged. Supplied services travel into child runs, durable hosts, and HTTP consumers. Creation options require the remaining services described by `RequiredDepsOf<typeof wizard>`.

`run()` resolves when the run is done, failed, cancelled, halted, or waiting for a view or an external event. Sleeps and retry delays keep it running. A halted or waiting outcome includes a snapshot you can resume. Use `create()` when the caller needs to keep driving the same live run. Invalid creation input is a boundary error; step failures are outcome values.

## Definition options

| Option | Contract |
|---|---|
| `name`, `version?` | Identify the declaration and its snapshot version |
| `context` | Required creation boundary, a Standard Schema value or `boundary` helper |
| `events` | Payload boundary for each named event |
| `deps` | Services boundary, often `boundary.trusted<Deps>()` |
| `output` | Optional synchronous selector `({ context }) => value` |
| `on` | Wizard-level handlers for declared events |
| `correlate` | Extract a correlation id from each event's payload |
| `onFailure` | `'halt'` by default, or `'compensate'` |
| `retry`, `autoRun`, `concurrency` | Default retry policy, `'ready'` or `'manual'` execution, work limit |
| `unmatchedEvents` | `{ buffer, ttl }` for events with no active listener |

`steps(map, { start? })` checks references and dependency cycles. `start` is one id or a nonempty array of ids; it defaults to the first map key.

Without an `output` selector, a done outcome contains the last completed sink step's output. A sink has no static successor in `next` or `targets` and is not consumed by another step's `needs`. Fallback and wait-timeout edges are alternate paths, so they do not remove a step's sink role. Branches and skipped steps can make the inferred output include `undefined`. Use an explicit selector when several terminal branches must produce one stable output shape.

## Step constructors

Every constructor takes an object configuration.

| Constructor | Output |
|---|---|
| `step({ run, ...options })` | Callback or adapter result, including an adapter returned by the callback |
| `step({ each, run, concurrency?, key?, ...options })` | Item results in input order |
| `step({ waitFor, timeout?, ...options })` | Resolving handler value or payload |
| `step({ sleep, ...options })` | `undefined` after a durable timer expires |
| `step({ next, ...options })` | `undefined`; routing or join without a work callback |
| `view({ input, ...options })` | Validated view input |
| `child(childWizard, { context, ...options })` | Child wizard output; an array with `each` |

Common options are `next`, `targets`, `needs`, `when`, `enter`, `exit`, `on`, `label`, `description`, and JSON `meta`. `waitFor` belongs to a wait step; compose a wait and a runnable step when an event should trigger work.

A `waitFor` handler returns `{ done: value }` to resolve with that value, `{ keep: true }` to keep listening, or `{ fail: message }` to fail the step. Returning nothing resolves with the validated event payload. Put routing on the step's `next`; wait-handler results do not contain `next`.

When a wait's timeout expires, the step is skipped with reason `timeout` and `timeout.next` is activated. Its `next` is not taken and its `exit` hook does not run. A timeout adds nothing to its `OutputOf`: a required `needs` on the wait skips its consumer, and `{ optional: wait }` supplies `undefined`.

| Work-specific option | Contract |
|---|---|
| `output` | Validate a runnable step's result |
| `retry` | `{ retries, backoff?, baseMs?, factor?, maxBackoffMs?, jitter?, when? }` |
| `timeout` | Runnable deadline; waits use `{ after, next }` |
| `fallback` | Alternate step to activate after retries are exhausted |
| `idempotencyKey`, `compensate`, `mapError` | Interrupted-work recovery, undo callback, JSON error data |
| View options | `input`, `initial`, `validate`, `canEnter`, `canExit` |
| Child options | `context`, `deps`, `output`, `each`, `concurrency`, `key` |

`retry.retries` is the number of extra calls after the first one fails. `jitter` is between 0 and 1. `retry.when` receives the mapped error when `mapError` is present. Durations are milliseconds or strings such as `'250ms'`, `'15m'`, `'2h'`, and `'1d'`.

Declare inline `mapError` before `retry` when its `when` callback reads inferred mapped fields. A reusable mapper with typed parameters supports either property order.

For a mapped step, `each` snapshots its items when the step starts. `run` receives `item` and `index`; outputs stay in input order even when work completes out of order. Finished item results persist, so resuming or retrying the step keeps them.

`retry(step, { patch? })` accepts runnable steps and mapped child step steps, typed by `RetryStepId`. It keeps finished map items and retries failed work. `startStep` accepts only `RunStepId`; it does not start a child step.

A fallback marks the failed source step skipped with reason `fallback`, retains its error, and activates the alternate target. Each completed saga entry gets its own compensation `idempotencyKey`, stable across undo retries and resume. The forward call and its undo have distinct keys.

## Activation and data joins

| Option | Meaning |
|---|---|
| `next` | Push activation to one or several successors |
| `needs` | Typed data join that both gates and activates the consumer |

`needs` aliases reference step objects created earlier in the callback. `needs: { price }` provides `needs.price` with that step's output type. `{ any: [a, b] }` uses the first completed output. `{ optional: a }` waits for `a` to settle and supplies its output or `undefined`. A skipped required need skips its consumer; optional needs do not propagate skips. A step listed in the `targets` of a function `next` is the exception to activation. Only that function starts it, and its needs hold it until they are met.

References in `next`, `targets`, and `fallback` accept step ids or step objects. A function `next` requires `targets` and must return a listed target, an array of listed targets, or `null`. Non-chosen targets become skipped. A join whose needs can no longer be met fails with `DEPS_UNREACHABLE` instead of waiting forever. See [graphs](/advanced/graphs) for branching and joins.

Hooks receive typed `context`, `deps`, and `needs`. `update(patch)` merges context; `update(current => patch)` applies the function to the latest committed context. Runnable hooks also receive `attempt`, a stable `idempotencyKey`, `signal`, and `progress(value)`. Progress events are transient and do not enter snapshots or the persisted log.

## Boundaries

Any Standard Schema value, including Zod, Valibot, or ArkType, can validate data. `boundary` also wraps plain functions.

| Helper | Use |
|---|---|
| `boundary.parse(fn)` | Return a parsed value or throw |
| `boundary.guard(fn)` | Wrap a type guard |
| `boundary.assert(fn)` | Wrap an assertion function |
| `boundary.trusted<T>()` | Declare a type without a runtime check |

## Run options

Pass input separately to `wizard.create(input, options?)`. Options include `deps`, `instanceId`, `correlationId`, `store`, `key`, `autoSave`, `debounceMs`, `redact`, `onPersistError`, `clock`, `scheduler`, `ids`, `logSize`, and `eventIds`. Durable hosting supplies its own commit and timer barriers.

`eventIds: { ttl?, limit? }` controls persisted event deduplication, defaulting to `'24h'` and 1000 ids. `createMemoryStore()` is a core persistence store for tests and one owning process. Use a durable host when several processes share a run.

On resume, each run fires its overdue timers before recovering its own interrupted work. The parent resume commits before restored children resume; deadline ordering is per run.

## `Run` methods

Commands return success or failure values. Navigation returns `NavResult`; event delivery returns `SendResult`. Commands after disposal return `DISPOSED`; new subscriptions are inert.

| Group | Methods |
|---|---|
| Navigation | `start()`, `next()`, `back()`, `go(view)` |
| Input | `setInput(view, patch)`, `resetInput(view)`, `validate(view)` |
| Events | `send(event, payload, { eventId?, correlationId? })`, `attach(source)` |
| Work | `startStep(step)`, `startReady()`, `retry(step, { patch? })`, `skip(step)`, `invalidate(step, { cascade? })` |
| Lifecycle | `cancel(reason?)`, `compensate({ from?, reason? })`, `reset()`, `dispose()` |
| Wire | `dispatch(command, { expectedVersion? })`; decode untrusted input with `parseCommand(wizard, input)` |

`send` accepts the event boundary's input type. An `unknown` request body also passes through that boundary. A remembered `eventId` returns `{ ok: true, duplicate: true, delivered: [] }` without delivering again.

`DispatchOptions.expectedVersion` is `{ epoch, seq }`. The run checks it atomically when the command reaches the interpreter, after any asynchronous boundary parsing. An intervening change returns `STALE`. If cancellation aborts a navigation already in progress, that navigation returns `CANCELLED`.

| Group | Reads |
|---|---|
| State | `getState()`, `getSnapshot()`, `subscribe(listener)` |
| Outcomes | `result()`, `awaitResult()`, `awaitOutcome()`, `subscribeResult(listener)` |
| Current work | `whenIdle()`, `explain(step)`, `waitingFor()`, `progress()`, `readyViews()` |
| Events | `observe(listener)`, `log()` |
| Children and clients | `child(step)` or `child(mappedStep, keyOrIndex)`, `project(projection, scope?)` |
| Persistence and identity | `save()`, `id`, `epoch`, `wizard` |

`run.wizard` references the wizard that created the run. `awaitResult()` waits for a terminal result. `awaitOutcome()` also resolves at a recoverable halt or a view/event wait and keeps the live run open. `whenIdle()` waits for the current command drain and persistence barriers, not future timers or unfinished asynchronous hooks.

`waitingFor()` is a flat list of `{ kind: 'view' | 'event' | 'sleep', path, step, events?, deadline? }`. An empty path describes this run; a child path names its containing child steps. Mapped items add their input index as a string, for example `['batch', '0']`. Observed child events use the same paths. `expose.waitingFor: true` includes the flat list in a projection.

An ordinary child uses `run.child('fulfil')`. A mapped child requires an input index or exact stable key, such as `run.child('batch', 0)` or `run.child('batch', 'order-42')`. String selectors are keys, so `'0'` selects the key `'0'`, while `0` selects the first input item. These methods return the selected live child run.

Run statuses are `idle`, `running`, `waiting`, `halted`, `done`, `failed`, `compensating`, and `cancelled`. A halted run accepts recovery commands such as `retry`; a failed run is terminal. Step statuses are `idle`, `active`, `done`, `failed`, `skipped`, `cancelled`, `compensating`, and `compensated`.

## Projections and mirrors

`defineProjection(wizard, { expose })` exposes only listed fields. `defineProjection(wizard, { select, scope?, progress? })` maps state to a custom client shape. A select projection forwards progress only with an explicit per-step `progress` map, for example `{ work: true, nested: { child: { upload: true } } }`.

A projection works with its authored Wizard and chained `provide` variants. Separately authored definitions with the same name and arbitrary object clones are rejected.

For an expose projection, `expose.steps.work.progress: true` allows that step's transient progress events. Nested child steps need their own child spec. `expose.progress: true` adds only the `{ done, total, ratio }` summary to projected state.

For a mapped child step, `child: true` exposes a readonly array of child summaries. A nested `child` exposure spec produces a readonly array of projected child states. Both arrays follow input order and use `null` for items without child state. Ordinary child wizards expose one summary or projected state.

Import `createMirrorSource`, `createMirror`, `parseWireCommand`, and `parseFrame` from `@openwizard/core/mirror`. Snapshot frames carry projected state; progress frames carry a `step.progress` event and no state. See [projections and mirrors](/advanced/projections).

`mirror.child('fulfil')` scopes commands to an ordinary child; `mirror.child('batch', 0)` scopes them to a mapped item's input index. Mirrors require numeric indices for mapped children. With `optimisticConcurrency: true`, the mirror sends its last applied sequence with each command; a concurrent change returns `STALE`.

## Introspection, adapters, and errors

Import `inspect`, `toMarkdown`, `toMermaid`, `toJSONSchema`, and `formatTrace` from `@openwizard/core/inspect`. `replay(wizard, events, options)` rebuilds state without running hooks. `isChildEvent` narrows nested events; `RUN_EVENT_TYPES` lists emitted event names.

A `RunAdapter` is an object passed as `step({ run: adapter })`. It supplies a default output boundary and typed failure channel. A step-level `output` replaces that boundary; a step-level `mapError` maps the original failure and replaces the adapter's mapped JSON data. Adapter mapping, such as `runEffect(program, { mapError })`, remains the default when the step does not override it. `createRunFailure`, `isRunFailure`, and `RunFailure` describe adapter failure envelopes; `StepFailure` describes a failed step.

A run callback can return or await an adapter. This lets the callback infer `item` and `needs` before constructing it. Its metadata validates the execution result. Declare a static step `output` boundary when persistence must revive parsed values such as Dates; resume does not call the callback to discover a schema.

`WizardError` reports programmer and boundary errors such as `DEFINITION_INVALID` or `SNAPSHOT_INCOMPATIBLE`. `RunLifecycleError` rejects waiters invalidated by reset or disposal. `isWizardError` narrows an unknown error.
