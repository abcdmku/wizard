# Snapshots and migrations

A snapshot saves run state, item results, child snapshots, event buffers, and absolute timer deadlines. Resume it when a workflow must outlive its current process.

```ts file="packages/docs/snippets/advanced/resume.ts"
```

The example creates a run through `approval.create(input, { store, key })`. It auto-saves committed changes; `save()` waits for the write. Three hours later, `approval.resume(saved, options)` restores the wait, increments the epoch, and re-arms the 48-hour deadline with 45 hours remaining.

## What a snapshot contains

Definition name and version, run id, epoch, sequence, context, step records, drafts, navigation history, buffered events, retained event ids, timers, compensation state, and child snapshots. An `each` step also saves its input items and completed item results. A snapshot is plain JSON; dependency services and hook functions stay in code.

Declare step `output` when a saved value needs parsing back into a richer object. For example, `output: z.coerce.date()` restores a Date from its JSON string. This boundary must be part of the definition even when a run callback returns an adapter with its own execution boundary. Resume does not rerun the callback to discover a schema. JSON outputs need no additional boundary.

The same saved object can be resumed more than once. Core does not coordinate those processes. Use a durable host if they could perform side effects against the same run.

## Interrupted work

A snapshot may contain runnable work that was active when the process died.

- Non-idempotent work fails with `kind: 'interrupted'`. Check the remote system before retrying.
- Idempotent work reissues with the stored `idempotencyKey`. The remote service must deduplicate it.
- Completed `each` items keep their results. Recovery only concerns unfinished items.

```ts
resumed.explain('notify').reasons // ['failed:interrupted', ...]
await resumed.retry('notify')
```

Default step failure policy produces a recoverable `halted` run. A failure under the compensation policy can end as terminal `failed`.

## Timers across restarts

```ts file="packages/docs/snippets/advanced/patterns.ts" lines="41-46"
```

`sleep` stores an absolute deadline and completes when due. Its duration can also be a function of hook arguments. Persist the run to preserve that deadline across restarts; a promise kept in memory cannot do this.

On resume, a run processes its overdue deadlines before its own interrupted work and buffered events. Parent runs resume before child restoration, so this is a per-run guarantee. Future timers use their remaining delay.

## Migrate old snapshots

Name and version identify compatible code. A name mismatch is rejected. For a version mismatch, pass a migration to the new wizard:

```ts
const resumed = approvalV2.resume(saved, {
  migrate: (snapshot, from) => {
    const v1 = ApprovalV1Snapshot.parse(snapshot)
    const identity = { name: from.name, version: 2 }
    return {
      ...v1,
      wizard: identity,
      state: {
        ...v1.state,
        wizard: identity,
        context: { ...v1.state.context, currency: 'EUR' },
      },
    }
  },
})
```

`ApprovalV1Snapshot` is your boundary for the saved v1 format. Parse the unknown input before reading it. Update both the envelope and `state.wizard`; normal snapshot validation still runs afterwards. Keep migrations deterministic and test saved fixtures for every supported version.

Use `resumeAsync` for an async migration or async snapshot validation. A synchronous resume does not accept a promise from its migration.

## One owner per run

Core sequences writes within one process so an older snapshot cannot overwrite a newer one. It has no cross-process lease or compare-and-swap protocol. Snapshot saving also happens after committed changes; it is not a database transaction around remote effects.
