# Retries and idempotency

A runnable step can retry with backoff, store a typed error, and pass an idempotency key to a remote service. Use these together when a crash could leave you unsure whether a request took effect.


When the ledger is down, the step remains `active` with `phase: 'retrying'` and an absolute `retryAt` deadline. `retries: 3` allows three retries after the first call. With a 200 ms exponential base, those delays are 200 ms, 400 ms, and 800 ms. Once retries run out, the default policy puts the run in `halted` so an operator can repair and retry it.

## Retry policy

```ts
retry: {
  retries: 3,
  backoff: 'exponential',
  baseMs: 200,
  factor: 2,
  maxBackoffMs: 30_000,
  jitter: 0.2,
  when: (error) => error.code === 'LEDGER_UNAVAILABLE',
}
```

A numeric `backoff` sets a fixed delay. `jitter` varies it to spread concurrent retries. `when` can stop retries for a permanent error and receives the mapped error when `mapError` is configured.

Retry deadlines appear in events and snapshots. Resume uses the remaining delay rather than restarting it. Use `createTestScheduler()` from `@openwizard/core/testing` to test deadlines without sleeping.

## Typed error data

`mapError` returns a small JSON-safe value for application code. `ErrorOf<typeof syncInvoiceFlow, 'post'>` recovers its type. The record keeps it in `steps.post.error.data` alongside the serialized error message. A non-JSON mapper result fails the step.

Raw thrown values may contain secrets or unstable library fields. Map the fields your UI or retry policy actually needs.

## Recover a halt

```ts
await run.retry('post', { patch: { amount: 125 } })
```

`halted` is recoverable. The run keeps its error, attempt count, completed outputs, and log. `failed` is terminal, for example after the compensation policy ends a run. `awaitOutcome()` reports a halt; `awaitResult()` keeps waiting for a terminal result.

For an `each` step, every item follows the retry policy independently. Exhausted items fail the step without discarding completed item results. An explicit retry reruns failed items rather than the whole collection. This applies to mapped child flows too: `run.retry('batch')` retains completed child outputs. `RetryStepId<typeof wizard>` includes runnable steps and mapped child-flow steps.

## Crash recovery needs service idempotency

<Diagram name="recovery" />

The worker can die after the ledger applies a request but before the run records its result. Mark `idempotencyKey: true` only when reissuing that request is safe. A runnable hook receives `idempotencyKey`; pass it to the service that performs the side effect. Retries and interrupted-work recovery reuse the key. A custom `idempotencyKey` function can derive the service's key.

Without `idempotencyKey`, resume marks an interrupted runnable step failed with `kind: 'interrupted'`. Check the remote system before retrying. Saving snapshots or deduplicating inbound commands cannot close the crash window around a remote call.

## Continue through a fallback


After `remote` exhausts retries, it becomes `skipped` with reason `fallback`. Its record retains the error, and `cache` activates instead of the run halting or compensating.

Fallback and event-timeout edges are alternate paths. They do not replace the successful step's sink output. If the wizard has several sinks, use its options-level `output` selector for one stable result shape. Otherwise its inferred output includes the possible sink values and, where branches can skip them, `undefined`.
