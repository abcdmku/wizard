# Multi-worker durability

Two workers can resume the same snapshot and both charge a customer. `@openwizard/durable` gives one worker a lease, fences its writes, and adds compare-and-swap commits, command deduplication, and timer claims.

## Own runs through a host

```ts
const runs = createDurableHost(wizard, { store, ownerId: 'worker-a' })
const opened = await runs.create('orders/o-1', { orderId: 'o-1' })
if (!opened.ok) {
  // LEASE_BUSY includes retryAt; opening a missing key returns RUN_NOT_FOUND.
}
```

The host owns renewal, terminal lease release, reopening, and disposal. Use `runs.open(key)` for an existing run, `runs.send(key, event, payload, { eventId })` for events, and `runs.dispatch(key, command, { commandId })` for commands. A provided wizard carries its bound dependencies; `deps(key)` supplies remaining services when required.

Handles returned by this host reacquire the current lease generation for `send` and `dispatch`. Their `run` property is the current local run generation; direct commands and subscriptions on it live only as long as that lease. Use host methods across I/O awaits or automatic terminal release. Explicit release or disposal ends that handle's lifecycle.

Use `createMemoryDurableStore()` in tests and [`@openwizard/drizzle`](/packages/drizzle) for PostgreSQL or SQLite. Store implementers import the protocol from `@openwizard/durable/store` and its conformance suite from `@openwizard/durable/testing`.

## Command ids and event ids

```ts
await runs.dispatch(key, command, {
  commandId,
  digest,
  expectedVersion,
})
await runs.send(key, 'payment.captured', payload, { eventId: webhookId })
```

A completed `commandId` replays its stored result across workers. Reusing it for a different digest returns `DEDUPLICATE_CONFLICT`. An expected-version mismatch returns `CAS_CONFLICT` with the actual version.

An `eventId` deduplicates event delivery through the run's bounded snapshot retention policy. It is separate from replaying a command result. Use the original provider delivery id and keep retention long enough for its retry window.

## Fence HTTP request claims

The [HTTP adapter](/packages/http) can store a response under an `Idempotency-Key` or `webhook-id`. Its `IdempotencyStore.claim(key, fingerprint)` returns a fresh `claimId` when ownership is acquired. `complete(key, claimId, response)` and `release(key, claimId)` must atomically verify that the live pending record still belongs to that claim.

If a claim expires or is evicted, an old request must not complete or release its replacement. The store returns `false` for that old identity. Share a database-backed store across workers; the memory implementation owns claims within one process. This response-cache claim is separate from the durable host's fenced command receipt.

## Commit before effects

The host installs a core commit barrier. It writes staged state under the fence before newly planned runnable hooks, child work, or timers begin. Public readers continue to see committed state while that write is pending. A failed commit stops the local run before its new effects execute.

The state commit still cannot transact with a remote service. A worker can crash after the service applies a request and before its result reaches the snapshot. Mark safe-to-repeat work `idempotencyKey` and send its stable key to that service.

## Recover command results after a crash

When a command reaches its final result, the store saves that result atomically with the snapshot for that command or its final navigation transition. A retry can replay it even if the worker stopped before replying.

If an async navigation command was applied but the worker stopped before its final transition result committed, the host returns `COMMAND_INTERRUPTED`. It does not execute that claimed command again. Read the run state and reconcile the operation before issuing a new command id. Command replay prevents reapplying recorded intent; it does not guarantee exactly-once external effects.

## Failover and timers

After a lease expires, another worker takes a new fencing token and resumes. An old owner's late write fails the fence; that host stops and its later local calls return `LEASE_LOST`. An interrupted idempotent hook may run again under the new owner with the same key.

A timer claim checks its due time and expected snapshot version. The completion marker and next snapshot commit atomically. Duplicate or stale claims cannot apply the same recorded deadline twice; side effects started by that deadline still need their own idempotency.
