# Explain, observe, replay

`explain()` reports why a step is blocked. `observe()` streams committed events and transient progress. `replay()` rebuilds state from recorded events without performing work. Use them to diagnose a stuck run or reconstruct an audit trail.

```ts file="packages/docs/snippets/advanced/inspection.ts"
```

The example observes a contact view, sets its input, and advances. It then replays the committed events and compares the result with `getState()`.

## Inspect the definition or explain a run

```ts
import { inspect, toMarkdown, toMermaid } from '@openwizard/core/inspect'

const graph = inspect(wizard)
const diagram = toMermaid(graph)
const page = toMarkdown(graph)
const explanation = run.explain('contact')
```

`inspect` reads the wizard's graph without creating a run. `toMarkdown` turns it into one page with the diagram, a table of every step, each step's needs and policies, the schemas, and the warnings. The page is the same for the same definition, so you can commit it and fail a build when it drifts.

The manifest includes data needs, control gates, declared routing targets, fallback edges, and warnings such as exclusive-branch AND-joins or ambiguous default output.

`explain(step)` reads live state. It emits no events and starts no work, even after disposal. It returns stored status, live phase, ready view candidates, blocking reasons, and `waitingFor`.

| Reason | Meaning |
|---|---|
| `flow-not-started` | `start()` has not run |
| `not-activated` | No start, edge, or satisfied data need activated this step |
| `deps-unmet:normalize` | A control gate or data need is still unmet |
| `guard-false:canEnter` | The entry guard rejected navigation |
| `concurrency-limit` | Runnable work is waiting for a slot |
| `auto-run-manual` | Use `startStep()` or `startReady()` |
| `flow-halted` | Repair or skip the failed work before continuing |
| `failed:interrupted` | Resume found non-idempotent work in flight |

`run.waitingFor()`, `explain().waitingFor`, and a waiting outcome use one flat list. Each entry has `kind: 'view' | 'event' | 'sleep'`, `step`, a relative `path`, and optional event names or deadline. An empty path means this run. Ordinary children use paths such as `['fulfil']`; mapped children include their numeric input index as a string, such as `['batch', '0']`. Progress events use the same public paths.

## Apply a command to the version you read

```ts
const { epoch, seq } = run.getState()
const result = await run.dispatch(
  { type: 'next', from: 'contact' },
  { expectedVersion: { epoch, seq } },
)
```

`DispatchOptions.expectedVersion` checks both epoch and sequence when the interpreter processes the command. The check still holds if payload parsing awaited an async boundary first. A mismatch returns `STALE`; read the latest state before deciding whether to retry.

`from` guards which view the command leaves. `CANCELLED` reports an aborted navigation transaction, for example when cancellation stops a pending guard. It is separate from `STALE`, which reports a version mismatch.

## Outcomes and terminal results

`awaitOutcome()` returns when the run is terminal, halted, or waiting on a view or external event. It keeps the run alive. `awaitResult()` waits for a terminal `done`, `failed`, or `cancelled` result, so it can stay pending while a run is halted.

`wizard.run(input)` creates and starts a run, awaits its outcome, then disposes it. A halted or waiting outcome carries a snapshot for later resume. Pure sleeps and retry backoff keep it running. Step failures become outcome values. Invalid creation input still fails at the boundary.

## Observe and retain events

Events carry `instanceId`, `epoch`, `seq`, timestamp, `type`, and a path relative to the observed run. Child events use their own sequence. Devtools and OpenTelemetry consume this stream too.

`log()` retains the last 200 recorded events by default; raise `logSize` for debugging. Stream committed events to external storage for a full audit. A ring that has lost the start cannot rebuild the initial state.

Hook `progress(value)` and `each` item progress emit transient `step.progress`. They are visible to observers but never enter the log or snapshot and do not consume the log limit. Keep durable business facts in context or outputs.

## Replay recorded facts

`replay(wizard, events, options)` invokes no runnable hook, event handler, compensation, or timer. `upTo` stops at a sequence for time travel; `from` starts with saved state when the event list is only a tail.

Root replay ignores child-path events; parent `child.summary` events carry the parent's facts. Replay proves what follows from recorded data. It cannot prove that a remote service reported the truth.

## Progress summaries

```ts
run.progress() // { done, total, ratio }
```

This counts workflow steps, including skipped work as finished. It estimates neither elapsed time nor collection size. Use an `each` step's `{ done, total }` progress events for item counts, and a hook's own progress payload for domain-specific work.

Progress stays private on a mirror unless the [projection opts in](/advanced/projections).
