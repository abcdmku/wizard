# External event routing

An external event passes its boundary and correlation check before the runtime delivers it to active listeners. If no step listens yet, the run can buffer it. Use this for webhooks that arrive early, twice, or for the wrong run.

```ts file="examples/05-external-events/src/checkout.ts"
```

On `run.send('payment.captured', payload)`:

1. The event boundary parses the payload. An invalid payload returns `BOUNDARY_REJECTED` with issues.
2. `correlate` extracts the order id. A mismatch with the run's `correlationId` drops the event.
3. Active listeners handle the event in activation order. A `waitFor` handler completes or keeps its step waiting.
4. If no step listens, the event can enter the FIFO buffer until its TTL expires.

## Boundaries and correlation

```ts
const run = checkout.create({ orderId: 'o-1' }, { correlationId: 'o-1' })
```

Verify a webhook signature at the HTTP layer before sending its body to the run. The event boundary then checks the payload before any handler reads it. Typed `send()` uses the boundary's input type; an untrusted `unknown` body still goes through runtime validation.

Correlation checks routing, not caller authority. Authenticate the sender and look up the run within its tenant before calling `send()`.

## Deduplicate deliveries

```ts
await run.send('payment.captured', payload, { eventId: webhookId })
```

The run records accepted event ids in its snapshot. Repeating one returns `{ ok: true, duplicate: true, delivered: [] }` without delivering it again. `eventIds: { ttl: '24h', limit: 1000 }` is the default bounded retention policy; adjust it in run options for your sender's retry window. An id outside that window can be accepted again.

Use a durable host when workers can race. Core's event-id record prevents duplicate delivery within the run; it does not make an external side effect exactly once.

## Buffer early events

`unmatchedEvents: { buffer: true, ttl: '10m' }` keeps a valid, correlated event until a wait enters. The runtime consumes the oldest matching entry first and drops expired entries. Set `buffer: false` when an early event is a caller error.

## Wait handlers and passive handlers

A `waitFor` handler can return `{ done: value }`, `{ keep: true }`, or `{ fail: error }`. A completed wait follows the step's configured `next`; its handler cannot return `{ next }`. Keep routing in the definition so `targets`, inspection, and skip propagation agree.

Views, runnable steps, and child steps can listen through `on`. Compose an event wait followed by a runnable step when the event should start work. A wizard-level `on` handler runs after step listeners. If a handler halts the run, the remaining handlers in that delivery do not run.

## Deadlines survive resume

An event wait can declare `timeout: { after: '30m', next: 'expired' }`. That is an alternate route if the event never completes the wait. On timeout the wait is skipped with reason `timeout`, so its output type never includes `undefined`. A step with a plain `needs` on the wait is skipped with it. The buffer, correlation id, event-id retention, and absolute deadlines are snapshot data.

On resume, a run fires its overdue deadlines before recovering its own interrupted work or delivering a buffered event. This ordering applies per run; a parent resumes before its children restore.
