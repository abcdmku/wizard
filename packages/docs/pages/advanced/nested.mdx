# Nested flows

A `flow(childWizard, options)` step runs a child wizard with its own run id, context, snapshot, and events. Use it when a stage needs its own navigation or recovery, or several parents reuse it.

## Context and dependencies

The child cannot read or mutate parent context. Its context mapper is the only way parent data enters it.

Parent dependencies pass through when they satisfy the child's remaining requirements. Add a `deps` mapper when they do not. `childWizard.provide(...)` carries bound dependencies into child runs, so a parent only supplies the keys still required. `DepsOf<typeof childWizard>` describes all services child hooks can read; `RequiredDepsOf<typeof childWizard>` describes what creation still requires.

## Reaching the child

```ts
const child = run.child('fulfil') // Run of the child wizard while it is live
```

An ordinary child takes no selector. Calling `child` before that run starts throws a `WizardError` with code `NOT_ACTIVE`. The parent record stores a child summary. `getSnapshot()` also embeds the full child snapshot, so resume can restore its work and deadlines. Disposing the parent disposes its children.

## Event paths

```ts
run.observe((event) => console.log(event.path, event.type))
// []          this run's events
// ['fulfil']  events forwarded from the child

run.child('fulfil').observe((event) => console.log(event.path))
// []          that child's own events
```

Paths are relative to the run you observe. An ordinary child's path is `['fulfil']`; a mapped child's path is `['batch', '0']` for input index zero. Further descendants append their step ids. `isChildEvent(event)` narrows a `RunEvent` to the child event family. Waiting and progress events use these same readable paths.

Mapped children require that second argument. Over the wire, `mirror.child('batch', 0)` uses a numeric input index; React uses `binding.useChild('batch', 0)` too. Ordinary children use only the step id.

If an item child fails, `run.retry('batch')` retries failed items while retaining completed results. See [retries and idempotency](/advanced/recovery) before repeating external effects.

## Failures cross the boundary

A halted or failed child fails its parent flow step under the parent's failure policy. A `fallback` on that step marks it skipped with the child's error retained and activates the recovery target. The child still has its own failure record for inspection.

If the child would contain only one function and no lifecycle of its own, use a runnable step. Nest when separate state or recovery helps.
