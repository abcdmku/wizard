# Compensation

When later work fails, compensation runs the undo hooks of completed steps, newest first. Use it when several external systems must agree and no single transaction covers them.

```ts file="examples/03-non-recoverable-compensation/src/book-trip.ts"
```

What happens when `charge` fails:

1. The runtime has recorded three completed runnable steps with their outputs.
2. `onFailure: 'compensate'` puts the run in `compensating` and starts unwinding.
3. `reserveCar`, then `reserveHotel`, then `reserveFlight` run their `compensate` hook with their own stored `output`.
4. The run ends `failed` with a compensation summary in state and in the result.

## Only completed work is compensated

A task joins the saga stack when it succeeds, and it stores the output its hook will need. A skipped, ready, or never-started task has no entry. Reverse order matters when a later reservation depends on an earlier one.

## Compensation can fail too

If the hotel cancellation throws, the runtime records that failure and keeps unwinding the rest. Once the hotel system recovers, retry just that entry:

```ts
await run.compensate({ from: 'reserveHotel' })
```

The hook receives the original output and an opaque `idempotencyKey` for that entry in the compensation stack. It stays stable across undo retries, save, and resume. It differs from the forward call's key; repeated loop executions get distinct undo keys. Pass the supplied key to the service rather than constructing one from the step id.

A worker can stop after an undo takes effect but before its result commits, so compensation may be repeated too.

## Match the service's undo operation

A refund does not erase a charge, and a cancellation may carry a fee. Write each hook to match what "undo" means for that service. Use the default recoverable halt when a human should repair and continue forward; use `onFailure: 'compensate'` when the path must end and earlier effects must be reversed.
